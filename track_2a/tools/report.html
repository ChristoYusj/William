1. Summary

Swiss parliaments publish their affairs (motions, postulates, interpellations, questions, reports) as PDFs, in German, French or Italian, at three levels (federal, 26 cantons, communes), each with its own layout and vocabulary. William turns such a document into one common, versioned structure, opd-affair/0.1, with Apertus-v1.5-70B. Every value carries the page and a verbatim quote it was read from. A value whose quote cannot be found in the document is removed. A classification without a quote is kept, but marked inferred.

The same pipeline ships in three forms: a Firefox extension that opens parliamentary PDFs in its own viewer, summarises the document or a selection in the document's language and links its political topics to Swiss news; a batch page (many links → JSON + PDF report); and an HTTP API with a web page for production use.

News about the affair. Next to the document, William shows the Swiss press coverage of the affair: the motion, question, vote or decision the document is about. Apertus names the political subjects of the document and writes a news query for each in the document's language. The subjects are highlighted in the summary, and clicking one lists the matching Swiss articles. For example, on a Lugano council answer to a parliamentary question, the reader gets the article “A Lugano ci sono volute 75 ore per rispondere a un'interrogazione”, about that same question.

On 14 OpenParlData documents (3 levels × DE/FR/IT, 14/14 processed), 154 values were verified against the source text, 85 proposed values were rejected (80 of them had no quote at all) and 67 classifications were kept as inferred. Headline insight: a common schema works for identity fields (number, title, original type term, addressee, authors; core-field coverage 0.76). It does not work, from the PDF alone, for procedure: 10 of 14 procedural states had no supporting quote, and no decision was verified in any document.

2. Architecture

link (PDF · HTML · api.openparldata.ch/v1/docs|affairs/ID · files.openparldata.ch/doc/…)
  ──► fetch + text per page (pdf.js in the extension, pypdf in the API)
  ──► OPD hints: body_key → level (CHE / canton / BFS no.), OPD type and number of the parent affair
  ──► Apertus 70B (shared/prompts.json, william-prompts/0.2) ──► JSON, one {v, p, q} per field
  ──► verifier: quote search on page p (normalised; space-insensitive fallback) ──► char span
        dates: day + month + year must be in the quote · numbers must be in the quote
        vocabulary fields: legal term or removed; no quote ──► status "inferred"
        type_original ──► fixed DE/FR/IT term lookup overrides the model's type
  ──► opd-affair/0.1 record + quality block (raw model output kept for offline re-verification)
  ──► summary in the document's language + topics ──► Google News RSS (CH edition) ──► inline highlights
  • One source of prompts and vocabularies (src/extension/shared/{prompts,vocab}.json), read by both the extension and the API.
  • Verifier written twice, checked identical: shared/core.js (extension) and src/william/{verify,extract}.py (API). tests/parity.mjs rebuilds the records of all 14 stored documents in both and finds 0 differences.
  • Extension (Manifest V2, Firefox ≥ 115): a blocking webRequest listener redirects PDF responses into the viewer (pdf.js with a selectable text layer; p.N evidence links jump to the page). Right-click menus summarise any selection or page on any website in a floating panel.
  • Batch page: three parallel workers; JSON download, or a PDF report written in the browser by a 150-line dependency-free PDF writer (shared/minipdf.js, checked by parsing it back with pypdf in strict mode).
  • API (src/william/api.py, FastAPI): /v1/extract, /v1/report, /v1/summarize, /v1/translate, /v1/schema, /v1/vocab, plus a CLI. It also serves the extension's batch page and viewer as plain web pages (/ext, /viewer), with a fetch proxy and an Apertus proxy so the browser never sees the key.
  • News for the affair: for each topic, Google News RSS (Swiss edition, document language; Italian restricted to Swiss outlets) is searched with progressively shorter queries. Articles are re-ranked by the content words they share with the topic, unrelated ones are dropped, and up to 5 are shown, with source and date, in the viewer, the in-page panel, the batch page and the PDF report (“In the Swiss news”).
  • Validator (python -m william validate, POST /v1/validate): checks any finished record against the schema, the provenance rules (page + quote for every extracted value) and the controlled vocabularies; --source fetches the document again and re-checks every quote on its page. All 14 sample records in data/sample/records/ pass.
  • Optional translation: Apertus translates the summary and key points into DE / FR / IT / RM / EN; the original-language summary is always kept next to it.
  • Key handling: in the extension the key stays in browser.storage.local; the API reads LLM_API_KEY from its environment and sends no CORS headers.

3. Use of Apertus

  • Model: swiss-ai/Apertus-v1.5-70B through the CSCS OpenAI-compatible endpoint; Apertus-v1.5-8B can be selected in the extension settings. LLM_NAME / LLM_BASE_URL / LLM_API_KEY follow the judges' convention.
  • How it is used: prompting-only inference at temperature 0, with JSON output and one stricter retry when the JSON is invalid or cut off. Apertus is used for:
    1. structured extraction, with a page and a verbatim quote for every field;
    2. the summary and key points in the document's language, plus 2–5 political topics with a news query each;
    3. optional translation of the summary (DE / FR / IT / RM / EN).
  • Prompts: src/extension/shared/prompts.json (william-prompts/0.2). The extraction prompt lists the controlled vocabularies (affair types, actor roles, procedural states, decision outcomes, relation types) and states that a quote is required for every value.
  • Cost: the 14-document extraction run used 46.2k input and 13.5k output tokens.
  • No other model is used anywhere in the pipeline or for evaluation.

4. Data

  • data/sample/urls.txt lists 14 OpenParlData documents: federal (CHE ×4), cantonal (GE ×2, TI, ZH) and communal (Bern 351, Zürich 261, Lausanne 5586 ×2, Lugano 5192 ×2), in German, French and Italian.
  • They are public parliamentary documents fetched at run time. Page texts are stored in tests/fixtures/ only for the offline tests; the stored Apertus outputs are in eval/.
  • There is no personal data beyond the names of elected officials as published by the parliaments. The extension and the API store nothing beyond the user's settings.

(c) Agreement with OpenParlData's own harmonized type (python -m william.evaluate crosscheck): 5/11 where both exist. The disagreements are informative:

  • Italian vocabulary trap. Ticino's interrogazione is a written question (OPD id 12); Apertus labelled it interpellation. A fixed term lookup on the verified original word now fixes this (+1, flagged in the record).
  • Document vs affair. A consultation report inside a parliamentary initiative, a committee report inside a government affair and a list of proposals are correct for the document but not for the affair → schema proposal document.type (docs/schema.md, Known gaps).
  • Possible OPD labelling inconsistency: a Ticino item I126.19 with the original term Interpellazione is harmonized by OPD as question.

Data-quality findings in OpenParlData itself. For at least two federal documents (e.g. doc 485241, “FF 2013 1073”), the stored file and text are the Fedlex “please enable JavaScript” page, not the PDF; William flags “source is listed as a PDF but the file is not a PDF” instead of extracting from it. OPD's state_name_harmonized_id is filled for 278 of 326,334 affairs (0.09 %) (/v1/affairs/group_by/states_harmonized, 16 Oct 2026).

Cross-parliamentary question: can the procedural state of an affair be read from its documents? OPD cannot answer this today (0.09 % coverage), and our answer is mostly no: William proposed a state for 14/14 documents, but 10 have no supporting quote (inferred) and the other 4 rest on weak quotes (a heading such as “Postulat”). Only one document (Zürich 261, a committee motion) yielded a decision, “recommended accept”, and it too had no verbatim basis. State and outcome should come from structured event data (OPD events / votings), with documents as evidence, not as the source.

6. Limitations

  • Long and scanned documents. Only the first 28k characters are read; longer documents are truncated and flagged. There is no OCR: scanned PDFs are flagged (“little or no text layer”), not processed.
  • One PDF = one affair. Bundles of several affairs per PDF are not split.
  • Packaging: the extension is unsigned (temporary add-on) and uses Manifest V2 for blocking webRequest (PDF interception).

7. Reproducibility

  • make test and make eval (Docker, no GPU, no API key) reproduce every number in §5 from the stored Apertus outputs in eval/sample_70b*.json and the page texts in tests/fixtures/.
  • make sample re-runs the sample extraction live (needs LLM_API_KEY); make validate checks the 14 sample records; make run starts the API and web page on port 8000; make extension zips the extension.
  • Apertus at temperature 0 is not perfectly deterministic on the hosted endpoint, so expect small differences in a live re-run. That is why the raw responses are shipped and all scores are recomputed from them.

8. Next steps
